# Засуха: правила и проверки

[Документация](README.md) · [Список испытаний](challenges.md)

`drought`, HARD/GLOBAL. Сервер постепенно удаляет источники воды вокруг живых игроков Survival/Adventure с активным испытанием. Creative/Spectator и мёртвые игроки не создают область; постройки и вода в общей области не имеют иммунитета по владельцу.

## Правила

- Область — цилиндр радиусом 6 блоков по горизонтали и ±3 блока по высоте от блока ног игрока. Граница включена. Центр следует за игроком, в том числе в транспорте; курсор обхода сохраняется при движении.
- Один общий проход каждые 5 серверных тиков, максимум 256 попыток проверки и 8 успешных испарений. При насыщении обход продолжается со следующей позиции, без очереди долга и обхода полного цилиндра за тик. Одна область содержит 791 позицию; без воды один игрок обходит её за четыре прохода (20 тиков). При нескольких раздельных областях обход дольше, общий бюджет прежний.
- Совпадающие области делят курсор. Раздельные области чередуются по одной позиции; пересечение не читает и не меняет один блок повторно за проход. Пропуски, в том числе из-за незагруженных чанков, расходуют бюджет попыток.
- Меняется только `FluidTags.WATER` с `isStill()`. Течение, лава, лёд и содержимое котлов напрямую не меняются. Waterlogged-блок теряет только `WATERLOGGED`, остальные свойства, блок и его BlockEntity сохраняются. Водные растения без этого свойства и пузырьковый столб не могут существовать без собственного источника и удаляются вместе с ним; опора/оборудование остаются.
- Вода ставится и собирается обычным ведром, пока её не посетил обход. В паре с `no_block_placing` действует существующий запрет установки. Новых ограничений взаимодействия нет.
- Используются обычные уведомления блоков и планировщик жидкости. Соседи могут восстановить источник, если это позволяют ванильные правила; последующие проходы испаряют его снова. Вода извне области может продолжать поступать. Запрета генерации источников и отдельной физики жидкости нет.
- Полив сохнет по обычным случайным тикам грядки, водные механизмы прекращают работу из-за потери воды. Нет отдельного мгновенного штрафа урожаю.
- Проверка чанка не загружает его; перед изменением нужны загруженные чанки самой позиции и её непосредственных соседей. Нет tickets/force-load. Далёкие и пограничные незагруженные участки пропускаются.

## Жизненный цикл

В памяти только курсоры владельцев и guard серверного времени/объекта PersistentState/activationSerial. Нет снимков воды, NBT испытания, отложенных изменений или списка испарённых блоков. Каждый проход заново проверяет игроков и текущую применимость; старые области после движения/смерти/выхода/смены мира не исполняются. Респаун и новый мир получают новый курсор; смена state/serial сбрасывает весь обход. Disable и остановка сервера освобождают память. Stop/reset/конец прекращают новые испарения; уже удалённая вода не восстанавливается. Ванильные отложенные обновления жидкости продолжаются.

## Автоматические проверки

Команды из корня:

```powershell
.\gradlew.bat runGametest --offline -I src/gametest/drought.init.gradle
.\gradlew.bat build processGametestResources --offline
git diff --check
git diff --cached --check
```

Свежий окончательный запуск 2026-11-20: **32/32 GameTest** — Drought 9, FireTrail 12, FragileFloor 4, NoBlockPlacing 7. Штатное завершение сервера с сохранением миров. Отчёт: `build/drought-gametest/report.xml`; лог: `build/drought-gametest-final-console.log`; мир: `build/drought-gametest/run`.

`build processGametestResources --offline` успешен, **199/199 JUnit**, без ошибок/пропусков; лог `build/drought-build-final-console.log`, XML `build/test-results/test/`. Все **58** штатных GameTest entrypoints восстановлены и сверены с исходным JSON. Production JAR `build/libs/curse-cycle-1.0.5.jar` содержит Drought и UTF-8 название, без GameTest/проб. Список совпадает с **64/64** уникальными ID реестра: 57 обычных + 1 специальное + 6 тестовых. Ресурсные JSON, UTF-8 и локальные ссылки документации проверены.

Новые проверки подтверждают точную границу цилиндра, источник/течение/лаву/лёд, настоящие использование/сбор/повторную установку ведром, пару с запретом установки, свойства лестницы и тождество/содержимое BlockEntity сундука. Проверяются Creative/Spectator/Adventure/PERSONAL, остановка/disable/reset, замена PersistentState/activationSerial, настоящие смерть/респаун/Fabric disconnect/вход и прямое изменение мира. Двадцать владельцев проверяют общий лимит попыток, прогресс при движении/пересечении и ровно восемь реальных испарений за проход. Незагружающий lookup проверен на недоступной позиции с неизменным числом загруженных чанков.

Два отложенных сценария используют настоящий END_SERVER_TICK и обычный планировщик жидкости: озеро 7×7 высыхает, после переключения новые источники сохраняются; контрольный источник 2×2 сначала действительно восстанавливает недостающую воду, затем высыхает при Засухе. Проверены пузырьковый подъёмник и грядка с контролем полива: после высыхания вызывается настоящий randomTick грядки и уменьшается влажность; пшеница сохраняется. Это не ожидание естественного случайного тика грядки.

Первый набор 31/32 выявил зависимость старого FireTrail budget-fixture от границ чанков случайного размещения: стенд теперь заранее загружает свой необходимый portal-search margin. Игровое условие FireTrail не менялось. Усиление контроля регенерации потребовало твёрдого дна под 2×2 и грядки на уровне воды; окончательный прогон после этих уточнений — 32/32. Локальный javap 1.21.1 подтвердил условия регенерации FlowableFluid, путь снятия WATERLOGGED и обычного randomTick грядки. Production не перехватывает эти методы.

## Ручные сценарии

В обычном клиенте активировать `/fdc activate drought`: проверить берег/большой водоём, ведро и waterlogging лестницы/контейнера, ферму и водный подъёмник; пройти через границу и сменить измерение. Снять переключением на другое испытание, проверить отсутствие новых испарений и возврата воды. Для пары: `/fdc activate "double_challenge:drought,no_block_placing"`.

Реальный GPU-клиент, два сетевых клиента, переход через настоящий портал, полный рестарт JVM, файловая выгрузка/загрузка чанка и нагрузка/FPS/MSPT не проверены. Лимиты алгоритма не являются измерением производительности. Новых клиентских Mixin, payload, зависимостей и ассетов нет.
